前言

《游戏编程模式》（Game Programming Patterns）结合游戏开发中的典型场景讲解设计模式：先用游戏视角重访GoF中最常用的几个模式，再介绍序列、行为、解耦、优化四类游戏专属模式。

什么是设计模式

  • 设计模式归根结底是因为编程语言的抽象能力不足而发明的。例如Listener（观察者）模式在C#中一个event关键字就能搞定，语言已经把模式做进了语法（语法糖）。
  • 设计模式之于面向对象设计，就如数据结构之于面向过程开发。只有真正理解设计模式，才算懂面向对象分析与设计。
  • 面向对象设计追求两点：高内聚、低耦合，即对修改封闭、对扩展开放。封装、继承、多态以及各种设计模式都是为这两个目标服务的。
  • 设计模式不是空理论。面向接口编程、优先组合而非继承、抽象与实现分离等原则在各模式中随处可见，尤其是组合（委托）与继承在耦合性上的差异。很多模式已扎根在开发平台中：Observer是MVC、MFC、Struts的基本框架，Iterator在STL中实现。
  • 即使系统很小，也值得学习设计模式。它体现的是一种思想，掌握后会不自觉地用于设计和开发，这比记住23种模式本身更重要。
  • 好架构的代码往往不是运行最快的；高度优化的代码则不灵活、难改动。架构和效率之间只能凭经验权衡。

一、重访设计模式

1. 命令模式

定义：将一个请求封装成一个对象，从而可以用不同的请求、队列或日志将客户端参数化，并支持撤销与恢复。通俗讲就是把方法调用封装进对象中回调。

  • 优点：类间解耦、扩展性强、命令易于组合维护、易与其他模式结合。
  • 缺点：类的数量会膨胀。
  • 使用场合：
    • 撤销、重做、回放、时间倒流等功能。
    • 录像与回放：执行一串预先录制、序列化的玩家操作命令（如游戏AI、Demo演示）。

2. 享元模式

定义：以共享的方式高效支持大量细粒度对象，复用内存中已有的对象，降低创建实例的开销。通俗讲就是很多对象共享同一块内存数据。

与单例的区别：享元强调共享内存，单例强调全局只有一个实例。单例可以看作特殊的享元。

两种状态：

  • 固有状态：不随环境改变，存储在享元对象内部，可以共享，所有享元对象中的值都相同。
  • 变化状态：随环境改变，不可共享，每个对象的值可能不同。
  • 享元的原理就是共享固有状态、区分变化状态，隔离系统中变与不变的部分。常配合对象池使用，往往不只为省内存，更为省时间。

使用场合：

  • 某类对象实例很多。
  • 对象的大部分数据可以变为固有状态。
  • 对象分类后，真正有区别的类别很少。

3. 观察者模式

定义：定义对象间一对多的依赖关系，一个对象状态改变时，所有依赖它的对象都得到通知并自动更新。通俗讲就是一方发送消息，所有注册了这条消息的对象都会收到通知。发送方叫被观察者，接收方叫观察者。

  • 系统拆成很多协作的类后，需要维护对象间的一致性，但又不希望它们紧密耦合，观察者模式就是用来解耦这类关系的。
  • MVC模式本质上基于观察者模式：数据与表现分离，通过收发消息交互。
  • 应用广泛：Java把它放进核心库（java.util.Observer），C#直接做进语法（event关键字）。
  • 使用场合：数据模块与UI表现分离；成就系统、小红点；服务端与客户端的数据通信。

2）用链表避免动态分配

真实项目中观察者列表会动态增减，频繁动态分配内存难管理也耗性能。容器无非数组和链表两种结构，改用链表，让观察者自己当节点，被观察者只保存头指针：

现在观察者数量不受限，添加和删除不产生动态分配，速度与数组一样快。

  • 侵入式链表：链表有两种风格，“节点包含数据”（教科书式）和“数据包含节点”（这里观察者自带_next）。后者侵入了对象定义，灵活性差但效率更高，Linux内核中很流行。
  • 限制：观察者本身就是节点，所以一个观察者同时只能存在于一个被观察者的列表中。通常是一个被观察者对应多个观察者，反过来少见，一般可以接受。
  • 多对多方案：改用“节点包含数据”风格，节点保存观察者指针和下一节点指针，多个节点可指向同一观察者。节点大小类型都相同，可预先在对象池中分配，同样避免动态分配。

3）野指针问题

删除观察者后，被观察者可能仍持有它的指针，再发通知就会访问已释放内存。

  • 最简单：观察者在析构时调用removeObserver()取消注册。观察者通常知道自己在观察谁。但难点不在怎么做，而在记得做。
  • 更安全：被观察者销毁时让观察者自动取消注册，在观察者基类中实现即可，不用每个人都记得。代价是复杂度增加：每个观察者要维护它所观察的被观察者列表，形成双向指针。

本质就是：先把监听者添加进容器，发送消息时遍历容器，触发对应监听。

请记住：

  • 观察者模式让发送者不必知道谁在接收，解耦互不相干的系统。
  • 用侵入式链表可避免注册/注销时的动态分配；需要多对多时用节点+对象池。
  • 销毁观察者或被观察者时必须取消注册，否则会出现野指针。

4. 原型模式

定义：用原型实例指定要创建的对象种类，并通过拷贝原型创建新对象。通俗讲就是拿一个对象做模板，克隆出新对象。

  • 注意区分浅拷贝和深拷贝。
  • 可以结合JSON等数据格式为数据模型构建原型。
  • 原型的类层次庞杂时管理起来很痛苦，所以实际常用组件模式和类型对象模式为实体建模，无需为每种实体建类。
  • 使用场合：
    • 创建对象过程复杂、初始化需要很多资源。
    • 希望框架原型和产生对象分开。
    • 同一对象可能被多个调用者同时访问。

5. 单例模式

定义：保证一个类只有一个实例，并提供访问它的全局访问点。

  • 核心就两点：唯一实例、静态全局访问。
  • 尽量少用：单例就是全局变量，有全局变量的所有弊病——代码更难理解、耦合更高、对并行不友好。
  • 单例同时解决了“唯一实例”和“全局访问”两个问题，但往往只需要其中一个。替代方案：
    • 子类沙箱模式：通过共享状态给实例提供访问，而无需全局可用。
    • 服务定位器模式：让对象全局可用，同时更灵活地配置。
  • 使用场合：系统中某个类只需唯一实例；游戏中的导演类、第三方库（物理、声音引擎）、文件系统、各种管理类。

6. 状态模式

定义：允许对象在内部状态改变时改变行为，看起来就像改变了自己的类。通俗讲：对象有多个状态，外部输入使它转移到另一个状态。状态、输入、转移就是这个模式的全部核心。

有限状态机要点：

  1. 拥有所有可能状态的集合。
  2. 同一时刻只处于一个状态。
  3. 一连串输入或事件被发送给状态机。
  4. 每个状态都有一系列转移，每个转移关联一个输入和另一个状态。

使用场合：很多MMO游戏的核心框架靠状态机维护——每帧检测当前状态，根据外部输入（摇杆、键盘）改变状态并执行操作。在简单有限状态机之外，还有并发状态机、分层状态机、下推自动机等扩展。即便如此状态机仍很受限，复杂AI现在多转向行为树和规划系统。

6）分层状态机

场景：站立、行走、奔跑、滑铲等状态都是“按B跳、按下蹲”。多个相似状态共用操作时，用继承减少重复代码，这就是分层状态机。

每个状态有一个父状态，子状态没处理的输入沿继承链交给父状态处理。

7）下推自动机

场景：按开火键进入开火状态FiringState，开火结束后要回到之前的状态。有限状态机没有历史概念，无法简单地回到上一状态。

下推自动机用状态栈代替单个状态指针：当前状态在栈顶，历史状态在下面。开火时把开火状态压栈，结束时弹出，自动回到开火前的状态。

请记住：

  • 状态模式把每个状态的数据和行为封装进各自的类，对象把行为委托给当前状态。
  • 状态无自身数据用静态实例，有数据（或多实例）时用new出来的实例。
  • 用入口/出口行为让状态自己管理自己的表现。
  • 并发状态机解决状态组合爆炸，分层状态机复用相似状态的行为，下推自动机支持回到历史状态。

二、序列模式

1. 双缓冲模式

定义：用序列的操作模拟瞬间或同时发生的事情。通俗讲就是用后台缓冲接收数据，填充完整后与前台缓冲交换，保证前台缓冲里的数据总是完整的。

要点：

  1. 双缓冲类封装一个被增量修改的缓冲，但希望外部把它看作一次性的整体修改。为此保存两个缓冲实例：当前缓冲和下一缓冲。
  2. 读取总是读当前缓冲，写入总是写下一缓冲。修改完成后一次交换，新缓冲公开可见，旧缓冲变为下一次重用的缓冲。
  3. 两点警示：
    • 交换本身需要时间，一般用指针交换。交换太慢就失去意义了。
    • 要保存两份缓冲，内存受限的设备上代价很大。无法接受时，只能用其他方法保证状态在修改时不被读取。
  4. 最常见的应用是帧缓冲交换：OpenGL的swapBuffers()、Direct3D的swap chain、XNA的endDraw()。

使用场合：同一块数据被多个对象同时访问的情况，最常见的是帧缓冲交换。显卡驱动通常已经提供了底层支持，这里讲原理帮助理解。

1）帧缓冲

帧缓冲可以看作一个二维数组，保存整屏像素数据，GPU从中读取并显示。写入和读取都是按顺序从左上角到右下角进行，且两者异步，可能读到还没写完的数据，导致画面撕裂、抖动。这与多线程中多个对象同时访问同一块内存的问题类似。

解决：前台、后台两个缓冲，写入后台缓冲，整屏写完后一次性交换到前台显示。

2. 游戏循环模式

定义：将游戏的进行与玩家输入解耦、与处理器速度解耦，即每个游戏都有的主循环。

  • 关键：控制游戏速度（帧率），并在CPU负荷与游戏效果之间权衡。
  • 任何游戏或引擎都有自己的游戏循环，它是游戏运行的主心骨。

1）从阻塞到非阻塞

最简单的阻塞式循环：

游戏在没有输入时也要继续运行（动画继续播放），所以真正的游戏循环是非阻塞的：处理输入，但不等待输入。

问题是循环跑多快？快机器上快得看不清，慢机器上慢得像爬。游戏循环的另一关键任务：不管硬件如何，以固定速度运行游戏。

2）固定帧率 + 休眠

想以60FPS运行，每帧约16ms。处理完一帧后等到下一帧时间：

处理得快时sleep()防止跑太快；但处理一帧超过16ms时休眠时间为负，游戏就会变慢，且永远追不上。

3）可变时间步长

把上一帧到本帧的真实时间传给update：

看似解决问题，但游戏不再确定，也不稳定：

  • 不确定：联网游戏中，快机器一秒更新50次子弹位置，慢机器只更新5次。浮点数每次相加都有舍入误差，更新次数不同误差不同，同一颗子弹在两台机器上落点不同。
  • 不稳定：物理引擎是真实物理的近似，为防止“飞天遁地”加了阻尼，阻尼被精心设计为以固定时间间隔运行，时间步长一变物理就不稳定。

4）固定更新时间步长，追赶真实时间

lag表示游戏时钟比真实时间落后多少。每帧用固定步长的内循环更新游戏，直到追上真实时间，再渲染。

5）渲染插值

更新步长固定了，但渲染发生在任意时刻，可能落在两次更新之间：

例如第三次渲染在两次更新之间，子弹应在屏幕中间，却仍显示在左边，看起来卡顿。

lag正好记录了渲染时刻距上次更新过了多久，把它占步长的比例传给渲染：

例如子弹在左边20像素处，以每次更新400像素的速度右移，在两次更新正中渲染时传入0.5，就画在220像素处，移动变得平滑。

这种推断可能出错（下一次更新时子弹可能撞墙或减速），但修正通常感知不到，比卡顿好得多。

请记住：

  • 游戏循环要非阻塞地处理输入，并让游戏速度与硬件无关。
  • 可变时间步长会导致不确定和物理不稳定。
  • 推荐：固定时间步长更新 + 用lag追赶真实时间 + 按lag / MS_PER_UPDATE插值渲染。

3. 更新方法

定义：通过每次处理一帧的行为来模拟一系列独立对象。通俗讲就是每帧更新游戏中所有对象（NPC、怪物、玩家……）。

  • 游戏维护对象集合，每个对象实现一个更新方法处理自己一帧内的行为，游戏循环每帧更新集合中的所有对象。
  • 离开每帧时，可能需要保存对象状态以备后用。
  • 使用场合（一般和游戏循环一起使用）：
    • 很多对象或系统需要同时运行。
    • 每个对象的行为与其他对象基本独立。
    • 对象需要随时间模拟。

这个模式简单而干净，它与游戏循环、组件模式是构建游戏引擎核心的铁三角。

示例：副本门口骷髅左右巡逻，雕像向进入范围的敌人发射闪电。

注意：用继承定义行为往往是糟糕的主意，庞杂的类层次难以管理，应多用对象组合而非类继承。真实项目中更应使用组件模式，让update()属于组件而不是Entity基类。这里为简单起见才用子类。

这个模式把游戏世界的构建和实现分开，也方便用数据文件或关卡编辑器构建世界。

请记住：

  • 每个对象实现update()处理一帧行为，游戏循环每帧遍历更新。
  • 更新方法、游戏循环、组件模式是游戏引擎核心的铁三角。
  • 优先用组件组合行为，而不是深层继承。

三、行为模式

1. 字节码

定义：将行为编码为虚拟机上的指令，赋予行为数据的灵活性，使其易于修改、易于加载，并与其他可执行部分隔离。

要点：

  1. 指令集定义了可执行的底层操作，一系列指令被编码为字节序列，虚拟机用中间值栈依次执行，组合指令即可定义复杂的高层行为。
  2. 可以类比项目中的转表工具（Excel转二进制数据读入工程），以及protobuf、json、xml的使用思路。
  3. 与GoF的解释器模式类似，都把数据与行为结合，且常一起使用：构造字节码的工具内部有对象树，编译时递归遍历它（就像解释器那样）；区别在于不是立即执行，而是先生成完整字节码再执行。

使用场合：

  • 用C++这类编译型语言开发时，策划频繁改数值、改表现。大项目的痛点在编译时间；已上线项目还要重新出包；遇到错误程序直接崩溃。
  • 思路：把行为和游戏主逻辑隔开，用分离的数据文件定义行为，引擎加载并“执行”它们——把行为转换为数据。
  • 这相当于开发自己的编程语言：定义指令集，实现编译器（自定义语言 → 字节码）和解释器（执行字节码）。Lua等脚本语言就是这样发展而来的。
  • 注意：字节码比本地机器码慢，不要用在引擎对性能敏感的部分。

2）虚拟机器码

机器码密集、线性、底层，硬件直接执行，速度飞快，但不能让用户写机器码，也不安全。折中方案：定义自己的虚拟机器码，在游戏中写一个小模拟器执行它。它像机器码一样密集、线性、相对底层，但规则由我们定义，可以放进沙箱。

这个模拟器就是虚拟机（VM），它执行的虚拟机器码就是字节码。它兼具数据的灵活易用和比解释器更好的性能。

2. 子类沙箱

定义：用一系列由基类提供的操作来定义子类中的行为。通俗讲就是把公共操作封装进基类，子类不直接与外部模块耦合，耦合集中在基类处理。

  • 基类定义一个抽象的沙箱方法和若干提供的操作，都设为protected，表示只给子类使用。每个子类用提供的操作实现沙箱方法。
  • 使用场合（如果你写过非虚的protected方法，可能早已在用）：
    • 有一个能派生很多子类的基类。
    • 基类能提供子类需要的所有操作。
    • 子类之间有重复行为，想更方便地共享代码。
    • 想最小化子类和程序其他部分的耦合。

3. 类型对象

定义：创建一个类A来灵活地创建新“类型”，A的每个实例代表一种不同的对象类型。通俗讲：定义一个类型对象类和一个有类型的对象类，每个类型对象实例代表一种逻辑类型，每个有类型的对象保存描述其类型的类型对象引用。

要点：

  1. 基本思想是给基类一个品种类（Breed），而不是派生一堆子类。区分种类时只需要Monster和Breed两个类，而不是Monster、Dragon、Troll……每个怪物都是Monster实例，其Breed保存同种怪物共享的信息。
  2. 这个模式引出如何在不同对象之间共享数据的问题，GoF的原型模式用另一种方式解决同一问题。
  3. 与享元模式是亲兄弟，都在实例间共享数据。享元的目的是节约内存，共享的数据不一定代表“类型”；类型对象的重点是组织性和灵活性。

使用场合：需要定义不同“种类”的东西，而语言自身的类型系统太僵硬时。尤其是：

  • 不知道以后还需要什么新类型（如游戏支持增量更新，下载新怪物品种）。
  • 想在不改代码、不重新编译的情况下修改或添加类型。

四、解耦模式

1. 组件模式

定义：允许单一实体跨越多个领域，而这些领域彼此不耦合。

  • 单一实体跨越多个领域时，把每个领域的代码放入各自的组件类，实体简化为组件的容器。
  • 组件之间交互常用两种方式：直接保存需要交互的组件引用，或通过观察者模式发消息。
  • Unity引擎大量使用这种设计，因此易于使用。
  • 使用场合（通常用于定义游戏实体的核心部分）：
    • 一个类涉及多个领域，想让这些领域互相隔离。
    • 一个类越来越大、越来越难用。
    • 想定义一系列共享不同能力的类，但用接口无法得到足够的复用。

2. 事件队列

定义：对消息或事件的发送与处理进行时间上的解耦。在队列中按先进先出顺序存储通知或请求；发送时放入队列就返回，处理系统稍后再从队列中取出处理。

要点：

  1. 事件队列可以看作观察者模式的异步实现。
  2. 事件队列很复杂，对游戏架构影响广泛。中心事件队列是全局变量，通常作为大的交换站，游戏各部分都把消息发到这里。
  3. 强大不代表好：事件队列把状态包裹在协议里，但仍是全局的，仍有全局变量的各种危险。

使用场合：

  • 只想解耦发送者和接收者，用观察者或命令模式即可，复杂度更低。需要在时间上解耦时才使用事件队列。
  • 从推和拉考虑：代码A要B做事，A自然是“推”请求，B自然是在方便时“拉”请求。一端推、一端拉时，中间需要一个缓冲区，这就是队列比简单解耦多出来的部分。队列把控制权交给接收者：可以延迟、合并或忽略请求；发送者只管发，不能决定何时被处理。
  • 发送者需要回复时，队列不是好选择。

6）多线程

多核硬件上，常见策略是每个领域一个线程：音频、渲染、AI等。请求和播放已经通过队列解耦，只需保证队列不被同时修改：playSound()只是赋几个字段，不会长时间加锁；update()里用条件变量等待，有请求时才消耗CPU。简单修改即可线程安全。

请记住：

  • 事件队列是观察者模式的异步版本，在时间上解耦发送与处理。
  • 一端推、一端拉时用队列缓冲；接收者可以延迟、合并或忽略请求。
  • 环形缓冲区实现队列：无动态分配、缓存友好；队列也是跨线程通信的天然边界。
  • 中心事件队列仍是全局的，发送者需要回复时不适用。

3. 服务定位器

定义：提供服务的全局访问点，而不让使用者与具体实现类耦合。通俗讲：服务类定义抽象接口，服务提供者实现接口，独立的定位器管理服务，外部通过定位器间接获取服务。

要点：

  1. 一般用单例或静态类实现，提供全局访问点。和单例很像，只是多了一个间接层，使用者不直接接触具体服务类。
  2. 可以看作更灵活、更可配置的单例。用得好，以很小的运行时开销换来很大的灵活性；用得不好，带来单例的全部缺点和更多运行时开销。
  3. 核心难点：它把依赖（两块代码之间的耦合）推迟到运行时才连接。更灵活，但阅读代码时更难看出依赖了什么。

使用场合：

  1. 它是单例的亲兄弟，使用前比较哪个更适合需求。
  2. 让大量东西在程序各处都可访问是在制造混乱，最简单的建议：尽量少用。
  3. 优先考虑直接把对象传过去，这样解耦明确，能满足大部分需求；不方便传时再考虑单例。
  4. Unity的GetComponent()使用了这个模式配合组件模式；微软XNA框架把它内嵌到核心类Game中，每个实例有一个GameServices对象，可注册和定位任何类型的服务。

五、优化模式

1. 数据局部性

定义：合理组织数据，充分利用CPU缓存来加速内存读取。简单讲就是让要处理的数据在内存中连续存储。

要点：

  1. 现代CPU有缓存，读取最近访问过的内存附近的数据更快。让处理的数据排列在连续内存上，提高局部性，从而提高性能。
  2. 要避免缓存不命中，可能要牺牲一些抽象。越围绕数据局部性设计，就越要放弃继承、接口及其带来的好处。没有高招，只有权衡。
  3. 执行结构大致是 CPU ↔ 缓存（L1等）↔ 内存（RAM）。影响性能的不只是代码，数据组织方式也直接影响性能。优化目标是让CPU需要的数据刚好在缓存中，即让要处理的对象在内存中连续存储。

使用场合：

  1. 遇到性能问题时才用，不要用在不常执行的角落。优化后的代码往往更复杂、更不灵活。
  2. 确认性能问题确实由缓存不命中引起，否则这个模式没用。
  3. 简单的测量方法是手动加计时；要找出缓存不命中发生的次数和位置，需要用profiler等专业工具。
  4. 组件模式是缓存优化最常见的例子。任何要处理大量数据的关键代码都应考虑数据局部性。

排序很简单：激活粒子时，与第一个未激活粒子交换；粒子死亡时，与最后一个激活粒子交换。每次状态变化只需一次交换。

很多程序员对在内存中移动数据很敏感，但解引用指针的代价往往比移动数据更大，能保证缓存命中时移动数据反而更便宜。

代价：放弃了一部分面向对象。Particle不再控制自己的激活状态，不能调用activate()（它不知道自己的索引），激活粒子必须通过粒子系统。

前两种不命中：指针导致的不命中、连续数组中的对象不是连续处理的不命中。第三种：对象中有大量不常用的数据，白白占用缓存行。

例如AI组件中，动画、能量、目标位置每帧都用，而掉落数据只在实体死亡时才用：

现在每帧遍历时加载进缓存的就是真正要处理的热数据（指向冷数据的指针除外）。实际中冷热数据的界限往往不清晰，需要反复测试权衡。

请记住：

  • 先确认性能瓶颈是缓存不命中，再用这个模式。
  • 三种缓存不命中：指针追逐、跳过不活跃对象、冷数据占缓存；对应解法：连续数组、活跃对象前置、冷热分离。
  • 移动数据往往比解引用指针便宜；代价是牺牲部分抽象和面向对象设计。

2. 脏标记模式

定义：将工作推迟到必要时进行，避免不必要的工作。用一个标志位记录数据是否变化，没变化就直接用缓存结果，不重新计算。

要点：一组原始数据随时间变化，从原始数据计算目标数据需要一定开销。用脏标记追踪原始数据自上次计算后是否改变，原始数据改变时设置标记。标记未设置就用缓存的目标数据；已设置就重新计算。

使用场合：

  1. 原始数据转换到目标数据很耗时，都可以考虑。
  2. 典型例子：
    • 物体局部变换到世界变换的计算：从根节点沿父链把变换组合起来（矩阵相乘）得到世界变换，没有变化时不必每帧重算。
    • 场景图中没有变化的对象不必重新处理。
    • 文档存档：内存中是原始数据，磁盘上是目标数据，不需要实时存盘。
  3. 原始数据变化速度远快于目标数据使用速度时不适用：算出来的结果总会因后续修改而失效。
