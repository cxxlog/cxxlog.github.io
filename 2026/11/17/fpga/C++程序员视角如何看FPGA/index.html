C++程序员视角如何看FPGA

fpga C++ FPGA 2026/11/17

给 C++ 程序员的 FPGA 入门（大白话版）

这份只做一件事：读完能用自己的话讲明白 FPGA，目标仍是「能看懂、能对话」，不是会写 HDL。

路线是：前四章回答四个原理问题（是什么 / 怎么工作 / 擅长什么 / 不好做什么），第五到七章看实际长什么样（代码 / 数据怎么发出去 / 他们用什么工具），第八章用一个真实的并机故障场景把前面的判据完整用一次，最后三章是速查、常见误解和自测。

写在前面：C++ 程序员其实已经懂了一半

C++ 和 FPGA 的差别不在「能做什么」，而在「用什么方式做」。给够时间和存储，两边能算的东西是一样的，差别是代价的形状：

  • C++：一套固定硬件 + 可换的指令流。 同一个加法器被反复调用，第 1 步加、第 2 步比、第 3 步存……功能越复杂只是多跑几步，硬件不变。
  • FPGA：一堆零件 + 可换的接线。 为这件事专门铺一条流水线，每一步各占一块电路、同时存在、同时动。功能越复杂占的地方越大，但不会「越跑越慢」。

一句话：软件用时间换通用，硬件用空间换通用。 这句话能解释后面几乎所有「FPGA 怎么这么别扭」的疑问。

一、它是什么

1.1 一块「可以重新接线」的芯片

先把四个东西放一起看：

打个比方 强在 弱在
CPU（日常接触最多的） 一个万能工人，什么活都会干，但一次只干一件 灵活，改需求最快 时间不确定，要听操作系统调度
GPU 一大群工人，同一道工序一起干 大批量重复活，吞吐高 单个活儿什么时候干完仍不确定
FPGA 照图纸把车间重新装修一遍，专为这一道活造一条流水线 每个工位同时动、时间可数、能直接接硬件引脚 改一次要重新装修，慢
ASIC（专用芯片） 把这条流水线刻死在硅片里 最快、最省电、量产后最便宜 做出来就改不了

所以 FPGA 不是「更快的 CPU」，是「出厂时没定死用途、可以事后把电路长出来」的芯片。

「重新接线」不是真拿烙铁。芯片里躺着海量的小开关和一堆小零件，给它加载一个配置文件（叫比特流），文件决定哪些开关连通，电路就「长」出来了。换一个文件，同一块芯片就变成另一台机器。断电重来，又能换。

别误会：它不是运行时想变就变。通常是上电加载一次，之后整块芯片就是那块电路，跑的过程中不会自己改。（少数能局部换的特例不必管。）

1.2 为什么非得有这种东西

从一个熟悉的痛点讲：sleep_for(1ms) 实际睡多久，没人敢打包票；中断什么时候来、线程什么时候被唤醒、缓存命不命中，全都不确定。平时无所谓，但有些场合要的是「每一次都刚好在这一刻」：

  • 每 10 微秒准时采一个点，一点不漂
  • 32 路信号严格同一瞬间采，彼此不能差
  • 触发信号来了，到输出之间的延迟每次都一样，能写进指标里
  • 模型按固定步长跑，还要带真实功率装置

这些事 C++ 也能写，但会一直在跟调度、中断、锁、缓冲较劲，而且永远给不出「保证」。FPGA 在这儿的价值不是算得快，是确定。

二、它怎么工作

这一部分是全篇核心。只建立三个画面，就够了。

2.1 画面一：0 和 1 就是灯亮、灯灭

一根导线，电压高算 1、低算 0。不是「约定电压代表数字」这种抽象，是物理上就两种稳定状态，好传、好复制、不怕干扰。代码里的 bool，就是它的物理版。

位宽 = 并排几根线。 一个 16 位的采样值，是 16 根线同时各自亮或灭，一拍全传完；不是一个 bit 一个 bit 串着送。所以「并行」在硬件里不是优化技巧，是本来就这样。

对照 C++：uint16_t v 是一个盒子里装一个数；硬件里是 16 根线一起亮灭。

2.2 画面二：门 = 几个开关凑成的「自动判断」

晶体管可以先理解成一个用电压控制的小开关。几个凑一起，就能做「与 / 或 / 非」。

举个能脑补的例子：门禁规则是「刷了卡 AND 在上班时间」才开门。这就是一个与门——两根线各是 0/1，两根都亮，输出那根才亮。

关键的一步来了：

任何「看几个条件、当场给一个是/否」的判断，都能用开关搭出来。

办法很土但万能：把所有可能的输入组合列成一张表（真值表），写上每种情况该输出什么，照着表接线就行。FPGA 里更偷懒——干脆把这张表存成一个小本本（叫 LUT），输入当页码去查，输出就是那页上写的字，连开关都不用真搭。

对照 C++：return (a && b) || !c; 是一行表达式，CPU 要取指、执行、写回；硬件里它是一小块电路，输入一变，输出那根线自己跟着变，没有「执行」这回事。

但门只会当场判断，记不住过去。 它没有「上次是多少」的概念，也没有变量。想有记忆，得上第三个画面。

2.3 画面三：触发器 = 每个节拍按一次快门

时钟是全局节拍器（比如每秒响一亿次）。触发器做的事很简单：节拍一响，把此刻输入的样子拍张照锁住，然后一直举着这张照片，直到下个节拍再拍新的。

  • 一个触发器记 1 位，8 个就是 8 位，N 个就是一个 N 位寄存器
  • 「变量」在硬件里，就是一组这样的照片
  • 有了「上次是多少」，才可能有计数器、状态、流程

别误会：别把它想成定时器中断。没有中断、没有调度器、没有「来了才执行」——是每拍无条件一起翻，哪怕这一拍啥也没发生。硬件里的「等待」也是一个实实在在的状态，不是阻塞在某个 wait 上。

2.4 把三个画面叠起来：程序的三要素都有对应物

C++ 里 硬件里 大白话
变量 一组触发器 一组一直举着的照片
x = f(x) 每轮更新 门算 f(当前值) → 下个节拍锁回去 算新照片、到点换上
if / else 一个选择开关 按条件决定把哪根线接出去
for 循环 N 次 计数器数拍子；或干脆把 N 份电路全摆出来同时做 要么一个人干 N 次，要么 N 个人同时干
数组 / vector 定长的寄存器堆或片内小存储 柜子做多大，上板前就定死了
函数、递归、调用栈 没有直接对应 得展开成状态机，或者干脆在 FPGA 里造个 CPU
new / 动态内存 没有 没有堆，没有 malloc
一次函数调用 一个状态机从「等活」走到「干完」，持续若干拍 没有「调一下就返回」

再看那个最能说明问题的例子——算 100 个数的和：

  • C++：一个人拿一把算盘，加 100 次（同一个加法器复用 100 次）
  • FPGA：摆 99 个加法器连成一棵树，几拍就出结果（复用空间）

都是加法，能力一样。一个花时间，一个占地方。

2.5 一个完整小例子：连续 3 次超标就报警

需求：每来一个 16 位采样值，超过阈值就计数，连续 3 次超标才把报警线拉高。

C++ 里通常这么写（每来一个点跑一遍）：

硬件是这么干的：

  1. 16 根线同时进一个「比大小」的门组合 → 输出「超了 / 没超」（画面二）
  2. 这根结果线接到触发器上，每拍记一次「最近几次超没超」（画面三）
  3. 再用几个门判断「三次都超了」 → alarm 那根线常驻 1 或 0

最关键的差别：C++ 是「来一个数据 → 跑一遍代码」；硬件是「电路一直摆在那儿，数据自己流过去，每个节拍自己更新一次」。没有「走一遍」，它一直就在那儿算着。

一一对应，但一个在时间里走，一个在空间里铺开。

2.6 它是怎么被「写」出来的

流程大致是：

  1. 写描述：用 HDL 说明「有哪些模块、怎么连、每个节拍做什么」——不是「先做 A 再做 B」的步骤清单
  2. 工具翻译：综合、布局布线，把描述变成一张「哪些开关连通」的配置表（比特流）
  3. 加载：灌进芯片，它就成了那块电路

对照熟悉的 C++ 流程：写代码 → 编译 → 链接 → 运行。FPGA 多了最重的一步——布局布线（把电路摆进芯片、把线连好），而且还要检查每条路径来不来得及在一个节拍里跑完（时序收敛）。这一步一次几十分钟到几小时，改一点逻辑就可能全走一遍。

所以「就改一行」在软件里是五分钟，在硬件里可能是半天。这不是人慢，是流程本身如此。

三、它擅长什么

判断窍门：凡是「固定节奏、数据成流、每拍做同样的事、还要保证时间」的活，都是主场。 下面每一条，用 C++ 都能写，但都得跟不确定性较劲。

擅长 具体场景 为什么软件难受
时间精确、每次一样 定时采样、触发同步、实时仿真固定步长 调度、中断、缓冲都带抖动，给不出「保证」
很多路严格同时 多通道同步采集、多路 PWM 软件是轮流处理的，做不到真正同一瞬间
数据像流水一样来 滤波、抽取、对齐、组帧、打包 每拍做同样的处理，正适合流水线铺开
直接接硬件引脚 ADC、编码器、传感器、功率装置 中间隔了操作系统，就慢且不确定
延迟低而且可预测 硬件在环、保护逻辑、闭环控制 低延迟软件能做到，但「每次都一样」很难
算法固定、要省电省地方 嵌入式前端、便携设备 专用电路不做取指译码，没那层开销

一句话：CPU 的强项是「什么都能干」，FPGA 的强项是「这件事能保证每次都这样干」。

四、它不擅长什么

这块比上一块更值得记住，因为它决定了「什么该留在 C++ 侧」。

  1. 控制流复杂、分支多的逻辑
    if 套 if、状态变来变去、业务规则一大堆——软件只是多跑几步，硬件里每个分支都得真占一块地方。分支越多，面积越吃紧。

  2. 长度不定的数据、要动态内存
    字符串、vector、JSON、变长包、动态容器……硬件没有 new，柜子多大上板前就定死。要么定长硬凑，要么绕回去用软核，优势就没了。

  3. 递归、函数调用栈、异常
    没有直接对应物。得展开成状态机，或者干脆在 FPGA 里装一个小 CPU 去跑软件——那还不如直接用真 CPU。

  4. 需求老变、要快速迭代
    编译一次几十分钟到几小时，改一点全重来。原型阶段、业务逻辑天天改的场景，用 FPGA 是给自己找麻烦。

  5. 复杂但偶尔才跑一次的算法
    铺一整片电路只为了偶尔用一下，太浪费。这种就该让 CPU 那套复用机制去干。

  6. 依赖操作系统生态的事
    文件系统、上层网络协议栈、UI、数据库、动态链接库——这些本来就是「软件世界」的东西。

  7. 重浮点、超大查表、复杂数学
    能做，但面积和功耗代价大，通常不划算（真要用，往往换成定点数或专门的运算块）。

一条万能判断法：
固定节奏 + 数据成流 + 每拍做同样的事 → 适合 FPGA。
分支多 + 长度不定 + 要灵活改 → 留在 C++。
中间地带（比如系统里的通信、配置、界面、上位机）通常还是软件干，两边配合。

还有一个差别必须记住：软件写复杂了只是慢一点，硬件写复杂了是放不下、或者跑不到目标频率——那是物理限制，不是性能优化能解决的。

别误会：「电路能实现各种功能」不等于「适合实现各种功能」。能力等价，代价完全不同。

五、代码长什么样：HDL 语法扫一眼

前面说「不用会写一行 HDL」——这话仍然成立。但看一眼它长什么样很值：看完就能明白为什么常说「会 C++ 学 Verilog 反而容易翻车」。

5.1 先认名字

它们统称 HDL（硬件描述语言），用来「描述电路」，不是「写执行步骤」。

名字 大致风格 常见吗
Verilog 语法像 C，简洁灵活 国内最主流
VHDL 像 Ada，强类型、啰嗦但严谨 军工、航天、欧洲项目偏多
SystemVerilog Verilog 的超集，类型更丰富 验证 / 仿真用得多，现在也大量用于设计
HLS 写 C/C++，由工具翻译成电路 听着对 C++ 程序员最友好，但时序和面积不如手写，别以为能把上位机代码直接搬过去

别误会：HDL 不是「另一种编程语言」。写下的多行描述是同时成立的电路结构说明，没有先后、没有执行顺序、没有调用栈。

看到的 其实是什么 对照 C++
wire / reg 不是变量类型，是「这根线当场算出来」还是「一组触发器、每拍锁一次」（画面二 / 画面三） 更像「表达式」vs「成员变量」
[1:0] 位宽写死 = 2 根线，装不下自己截断 一个 uint2_t，没有「自动升级」这回事

<= 非阻塞赋值：这一拍所有右边同时算完，到拍沿一起锁进去 不是 x = x + 1 那种立刻改；同一拍里谁先谁后不重要
没有 main 没有入口、没有「从哪行开始跑」 所有 always 块一直在那儿同时跑

代码里那些 C++ 没有的东西，是真实工程绕不开的：

多出来的 为什么绕不开
module + 端口表 硬件模块得先声明「几根线进、几根线出」，位宽写死；没有函数签名那种灵活参数
din_valid C++ 里「每来一个点跑一遍」是循环 / 回调隐含的；硬件得有根线明说「这拍有点」，否则每拍都会算一次

末尾不写 else din_valid 为 0 时 cnt 自动保持原值——时序逻辑里这是「锁住」，不是漏写分支，也不会综合出锁存器

（再细一层：真实工程里复位通常还会做「异步复位、同步释放」来避开 recovery / removal 问题，这里为看清逻辑省略了。这段是讲对应关系的示例，不是可直接交付的 RTL 模板。）

别误会（一个真实的时序差别）：C++ 里第三个超标点处理完，alarm 当场就是 1；这里 cnt 要等时钟沿之后才变成 3，所以 alarm 会晚一拍拉高。想让它和 C++ 完全同步，得用组合的「下一值」去驱动输出，但那样组合输出有毛刺风险，工程上通常接受晚一拍、或把 alarm 也做成时序寄存。这不是写错了，是「一步接一步」和「按拍锁存」的天然差别。

最要紧的一句：C++ 是一行行往下走，HDL 是一行行同时摆着。交付的是「电路结构说明书」，不是步骤清单。

5.3 为什么「像 C」反而是坑

  • 以为有先后顺序 → 其实所有描述同时成立
  • 以为 if/else 是分支跳转 → 其实是个选择开关，两条支路对应的电路都在那儿，只是选哪根接出去
  • 以为 for 是循环 → 要么被展开成 N 份电路同时算，要么变成「计数器 + 状态机」数拍子
  • 以为赋值是覆盖变量 → 其实是「下个节拍这组触发器锁什么」
  • 以为能 printf、下断点、抛异常 → 都没有，看内部状态得靠波形

这节不是教程。目标是看到代码不懵，听得懂「这个信号打了一拍」「这里得用非阻塞赋值」「这段要展开成流水线」。语法细节和 Vivado 的具体操作不在本文范围——第七章末尾会说明为什么不必在这一层深钻。

六、数据怎么发出去：UDP 通信链路全流程

这节讲数据是怎么发出去的：从 send() 底下发生了什么，到 FPGA 侧怎么把协议栈铺成一片电路。也是最常见的一段软硬边界。

6.1 先拆穿 send()

一句 send(sock, buf, len, 0) 就完了，底下其实是一整条流水线：

  1. 调用方给出载荷和目的地址（IP / 端口早定好了）
  2. 内核加 UDP 头（端口、长度、校验和）
  3. 内核加 IP 头（源/目的 IP、校验和……），必要时先 ARP 查目的 MAC
  4. 加以太网头，凑成一帧
  5. 驱动把帧放进 DMA 环，网卡硬件从内存读出来
  6. 网卡加前导码、CRC、帧间隔，串化后交给 PHY 变成网线上的电平

关键洞察：真正把 bit 推上线的从来都是硬件，PC 上也是；软件只负责「把包组装好放在内存里」。所以 FPGA 不是干了什么新鲜事，只是把内核协议栈那一半也用电路做掉。

6.2 FPGA 侧缺了什么

没有操作系统、没有协议栈、没有 socket、没有 malloc，更要紧的是：没有「内存里放着一个包对象」这回事。数据是从采集侧一拍一拍流过来的字节流。于是：

  • 组包 = 按约定顺序，一拍往数据线上放一个字节
  • 包头不是结构体赋值，是「计数器数到第 N 个字节时，把这个位置该有的电平放上去」；固定字段查一张常量表，长度、序号、时间戳当拍现算
  • 包边界不是 len 参数，是一根 tlast 线在最后一拍拉高
  • 校验和不是「先算完再填」，是边流边算的一小片电路，数据过一遍结果就出来
  • 没有返回值：只有「这一拍 valid 和 ready 同时成立，数据成交了」。丢没丢，只有上位机那一侧知道

6.3 发送状态机：把协议栈铺成一片电路

典型发送侧就这几步：

状态 这一拍在干什么
攒数据 等 FIFO 够一包，定下包长 / 序号 / 时间戳
送以太头 计数器逐字节，从包头模板里把固定字段取出来
送 IP 头 长度、校验和由组合逻辑现算着填
送 UDP 头 端口、长度、校验和
送载荷 FIFO 按拍流出采样点，边送边喂进校验和电路
收尾 最后一拍拉高 tlast，补 CRC，回到攒数据

一个状态机 + 几个计数器 + 一张包头常量表 + 一条流式校验电路，就是「协议栈」。

对照总纲：PC 上协议栈是「时间」——OS 里一段跑着的程序；FPGA 上协议栈是「空间」——芯片里一片常驻的电路。一行 send() 背后是几万行内核代码，FPGA 把它压成这几样东西，每拍都在跑。软件用时间换通用，硬件用空间换通用，到这里又对上了。

七、他们用什么干活：Vivado 工具链

7.1 Vivado 是什么

Vivado 是 AMD/Xilinx 的全套开发环境：写代码、仿真、综合、布局布线、时序分析、生成比特流、下载、上板调试，全在里面。本文以它为例（Intel 阵营对应 Quartus + SignalTap，不在本文范围）。

别误会：别把它当成「FPGA 的 Visual Studio，写完点运行就行」。写代码只占很小一部分，最重的是综合、布局布线、时序收敛，一次几十分钟到几小时，改一点逻辑就可能全走一遍——这就是 2.6 里「就改一行等半天」的根源。

7.2 工具链，映射成熟悉的编译链

# FPGA 侧 大致相当于 C++ 侧
1 写 HDL / 搭 IP 核 写代码、加依赖库
2 仿真（testbench，看波形图） 单元测试 / 本地跑一遍
3 综合：描述 → 门和触发器的网表 编译
4 布局布线：把网表摆进芯片、连好线 链接 + 装进具体机器（CPU 上根本没这一步）
5 时序分析：一拍之内逻辑跑不跑得完 更像「能不能编译过」的硬门槛
6 生成比特流、下载到板子 产出可执行文件并部署
7 上板调试：ILA 抓内部信号波形 gdb / 线上 profiling

第 3～5 步是软件世界完全没有的一环，也是「慢」的全部来源。

7.3 几个会反复听到的名字

名字 是什么 关注点
Block Design / IP Integrator 画框图搭系统：把 MAC 核、FIFO、ILA、时钟模块拖进去连线 向 FPGA 侧要一张截图——一眼看出 FIFO 在哪、MAC 在哪、跨不跨时钟域、组帧在谁那边，比读代码快十倍
IP Catalog / IP 核 厂商做好的现成模块 「FIFO 多深」就是配置界面里的一个参数
XDC 约束文件 引脚分配 + 时序约束（纯文本） 改采样率、换引脚、时序不收敛，多半动这里
Synthesis / Implementation / Generate Bitstream 工具栏那一排按钮 「改一行等半天」就发生在这三步
Hardware Manager + JTAG 上板后连板子、下载比特流、看 ILA 波形 FPGA 侧说「抓一下」，实际是在这个界面
ILA 核 埋进设计的探针，要设「什么条件下开始抓」「抓多长」 这两个参数受片内存储限制，偶发问题很难设准触发

7.4 「抓包」和「抓波形」不是一回事

上位机侧说的抓包是 Wireshark 抓网络帧；FPGA 侧说的「抓一下」是 ILA 抓芯片内部一根根线的电平波形。两者能接起来：把探针挂到 MAC 核前面的流接口上，就能在包发出芯片之前看到每一个字节——这是定位「到底是 FPGA 没发、还是网口 / 上位机丢了」的终极手段。

别误会：ILA 不是 gdb。gdb 随时下断点看变量，ILA 的探针必须提前埋进设计并重新编译，能抓多久还受片内存储限制。所以偶发问题别一上来就让人抓，先加个状态 / 溢出计数寄存器往往更划算。

7.5 最省力的一步，以及一个呼应

不必装 Vivado、也不必学怎么点。向 FPGA 侧要一张 Block Design 截图 + 一份 XDC，对照第六章讲的 UDP 发送链路，把「采集、组包、发出、上位机接收各归谁」画出来——这就是软硬边界图的底稿。

最后呼应一下全文的定位：HDL 语法、Vivado 怎么点、ILA 怎么加探针，都属于随时可查的操作层，看一遍即可，不必深钻。真正值钱的还是前面那些判断：什么该放硬件、什么该留软件、失效该导向安全、边界怎么切。

八、一个真实场景：故障联锁该写在哪一侧

前面七章给了一堆判据，这章拿它们做一次真实决策。场景是电力仿真 / 功率装置里很典型的一种：

下位机是 FPGA，上位机是 C++ 做的，一一配对；局域网里有多组这样的设备，彼此是主从关系、并机运行。每台配对机器的并机状态目前由下位机固定上报。运行中某台机器故障了，要求停掉所有其它机器。

问题：这个「故障 → 全线停」的逻辑，是 FPGA 自己监测直接停，还是上位机监测到故障后发一条停止指令让下位机停？

结论先给：停机的执行与联锁必须写在 FPGA 侧，而且走独立的硬件联锁通道；上位机 C++ 只做监测、告警、记录、故障复位，以及一条冗余的「软急停」。绝不能让「上位机发现故障 → 发停止指令 → 下位机停」成为唯一或主路径。

8.1 三条理由，第二条最关键

一、时间尺度对不上，而且并机要求「同时」停。
上位机那条路径的延迟 = 上报周期 + UDP 往返 + 网卡 / socket / 采集线程 + OS 调度 + 解析判断 + 跨 PC 转发（这里还是多组、还分主从），最好十几毫秒，坏情况丢包、界面卡、线程被抢、上位机死机 → 无限长。功率侧故障扩散却是微秒到毫秒量级：一台输出短路，其它几台还在往母线上灌功率，就会倒灌、环流、连锁损坏。更麻烦的是并机不能「各自停各自的」——停得有先后，先停后停之间立刻产生均流失衡。多路严格同一瞬间正是第三章说的 FPGA 主场；上位机逐台发指令，物理上做不到同步。

二、失效方向反了，这是根本问题。

「发停止指令」这条路，是靠通信持续正常来维持安全：上位机活着、网通、包不丢、软件没卡，才发得出去。任何一环挂掉，结果是「不停」——失效致危（fail-dangerous）。

安全回路必须反过来：「跑」需要持续授权，「授权消失就停」（心跳 / 使能超时默认停）——失效安全（fail-safe）。

一句话记牢：停止不该依赖一条「发得出去的指令」，而该依赖「允许运行」这个条件被撤销。 上位机死机、断网、交换机掉电，系统应该自动全停，而不是继续跑。

三、依赖面和单点。
通用 PC + OS + Qt + 交换机，是整个系统里最不可靠的一层，让它独占「所有机器停不停」的决策权，等于把安全性押在最弱的部件上。而「主从」如果落到上位机，还多出「主上位机」这个单点：主的那台挂了，谁来发停？

8.2 顺带点破现状那句话

「并机状态是下位机固定上报的」——作为观测、显示、记录，完全没问题；但如果被当成「上位机据此判断要不要停」的依据，就是把安全挂在了一条「最好情况下才成立」的链路上。建议在接口文档里明确解耦：上报 = 观测数据，联锁 = 独立硬件通道，互不作为前提。

8.3 推荐的分层架构

层 谁 职责 时效
硬联锁（保护） 每台 FPGA + 机间专用连线 本机故障 → 无条件封锁本机输出；同时把故障电平广播出去，所有机同拍封锁 微秒到毫秒，不经任何软件和网络
全局「允许运行」 FPGA 之间（或主控单元） 汇总各单元 ok/fault，维护使能；心跳丢失、信号非法 → 默认停 每拍
监测 / 告警 / 记录 上位机 C++ 收状态、显示哪台故障、录故障前后波形、日志、报表 允许抖动、允许丢包
非紧急指令 上位机 C++ 正常顺序停机、参数下发、人工确认后的复位、界面软急停（冗余第二路径） 秒级，可走 UDP

8.4 落地时要守住的设计点

  • 用「使能 / 心跳」而不是「stop 命令」：下位机只在持续收到有效授权时才允许输出，撤销即停。上位机可以参与「续签」，但续签断了必须自己停。
  • 本机先自保，不等任何人确认：检测到故障的第一动作是无条件封锁本机脉冲，同拍或几拍内再广播，不要等主机裁决。
  • 故障要锁存：瞬态过流尖峰过后信号会消失，FPGA 里必须锁住故障标志，直到人工确认复位（复位指令由上位机发是合理的——它是需要人判断的非安全动作）。
  • 安全否决权别给「主」独占：主机管正常控制（同步、相位、给定值分配）没问题，但任一单元都得能拉停全线（故障信号做成线或 / 任一拉低即停），否则主机一挂，全系统失去保护。
  • 联锁别和业务 UDP 共用链路：走独立硬线 / 光耦 / 差分，或至少物理独立的链路。共享介质有丢包、交换机故障、广播风暴——第六章讲的那条 UDP 链路，本质上就是观测通道，不是安全通道。实在只能走网络，也必须做成 FPGA 直接解析 + 超时默认停，且优先级低于硬线。
  • 判据要简单、硬、明确：过流、过压、过温、驱动故障、使能撤销、心跳丢失——这类才适合放进硬件。复杂诊断（趋势、多条件组合、模型失稳判断）留给上位机。

别误会：这不是说 FPGA 万能。硬件侧的代价是真实的——误报（传感器毛刺）会误停、规则写死难改、调试要重编译、机间硬线有距离 / 地环路 / 抗干扰问题、复杂判据根本放不进去（第四章那七条）。所以边界是：**「该不该立刻停」用最简单的硬判据放 FPGA，「为什么停、怎么记录、怎么恢复、正常怎么按顺序停」留给 C++**。

还有一种容易走偏的情况：如果「故障」这个结论本身是上位机用复杂逻辑算出来的，也别改成「上位机发停」——正确做法仍是上位机持续续签心跳，续签一断就停，把失效方向扭回 fail-safe。

8.5 不推倒重来的渐进顺序

  1. 每台 FPGA 加「本机故障 → 立即封锁本机输出」的自保逻辑，不依赖上位机（改动最小、收益最大）。
  2. 加一条机间硬联锁（或复用现有并机同步线），做成「任一故障全停」+ 心跳超时默认停。
  3. 上位机退到监测 / 告警 / 录波 / 复位，停止指令降级为冗余软急停。
  4. 接口文档里写明「上报状态仅供观测」，避免后人拿它当安全依据。

8.6 落地自检清单

  • 从故障发生到全线封锁，允许的最大时间是多少？跟「上报周期 + 网络往返 + 调度余量」比一比，答案基本就定了。
  • 上位机死机 / 断网 / 交换机掉电，系统现在是什么行为？如果是「继续跑」，这是必须优先消掉的缺陷。
  • 故障信号会不会自动恢复？有没有锁存和人工复位？
  • 联锁链路和业务以太网是不是物理独立？
  • 主机（或主上位机）挂了，从机能不能自己停？
  • 有没有「允许运行」心跳超时机制？超时后默认状态是什么？

这一章就是把前面的尺子用了一次：要求确定性、且失效必须导向安全 → 归硬件；要人机、要记录、要灵活、要恢复 → 归软件。第三章「擅长」和第四章「不擅长」，到这儿不再是两张表，而是一个要签字负责的决定。

十、几个最容易踩的误解

  1. 「FPGA 是更快的 CPU」 — 不是。它没有指令集、没有操作系统、没有线程，连「执行到哪一行」都不存在。
  2. 「会 C++ 学 HDL 应该很快」 — 像的是拼写，不是思维。HDL 写的多行描述是同时成立的电路结构，没有先后顺序（第五章有对照代码）。
  3. 「FPGA 里能跑 C++」 — 能（HLS 或内部装个软核），但那样等于退回通用指令流，通常就把 FPGA 的优势丢了。
  4. 「电路能实现各种功能，所以什么都能往上搬」 — 见第四节，能力等价不等于代价合适。
  5. 「仿真跑通了，上板就没问题」 — 仿真里的信号是理想的；时序收敛、引脚电气、真实干扰这些只在板子上才冒出来，工具链里最重的几步恰恰是为它们准备的。

十一、读完自测

能用自己的话说出下面六句，这份就到位了：

  1. 是什么：一块出厂没定用途、靠加载配置文件「长出电路」的芯片；不是更快的 CPU。
  2. 怎么工作：电平(0/1) + 门(当场判断) + 触发器(每拍拍张照记住)；程序的三要素都有对应物，只是把「一步步」摊成「一片同时存在」。
  3. 擅长：固定节奏、多路同步、数据成流、要求时间确定的活。
  4. 不擅长：分支多、长度不定、要动态内存、需求老变、依赖 OS 生态的活。
  5. 实际长什么样：代码是「同时摆着的电路说明」，UDP 包是状态机一拍一拍拼出来的字节流，工具是 Vivado 那条比编译链更重的流程——这三样看懂即可，不必会写。
  6. 会切边界：给一个真实场景，能用「要求确定性 + 失效必须导向安全 → 硬件；要人机 / 记录 / 灵活 → 软件」判断该写在哪一侧（第八章）。

再记一句总纲：软件用时间换通用，硬件用空间换通用。
